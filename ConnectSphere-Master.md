This document gives developers and coding agents the durable context needed to build ConnectSphere. It defines the repository layout, architectural boundaries, roles, business rules, data ownership, workflow guarantees, test expectations and agent workflow.

This document intentionally does **not** define a route-by-route API contract, request/response payload catalogue, OpenAPI specification or deployment/runtime architecture. Ticket acceptance criteria, implemented route definitions and tests determine the transport details for each feature. When a ticket changes an enduring business rule or structure, update this master in the same work item.

## Changes from 1.13

Version 1.14 applies the developer decision of 1 November 2026 on tentative holds (Jira SPM-190, SPM-188). A booking request is the venue hold: when the assigned coordinator sends venue booking requests to Venue Staff, each `PENDING` request occupies its venue (setup and turnaround included) until Venue Staff approve it (it becomes the booking) or reject it (the venue is released), or until its hold expires. Week 7 change 4 still applies: the hold has an expiry, the venue is released when it passes, and the coordinator is told 24 hours before and at expiry. Holds are handled by the backend only; no role sees a holds section, hold filter, hold count or hold label.

## 1. Architecture Decision

ConnectSphere is a **modular monolith**, not a microservices system.

- The browser application is a separate Next.js repository.
- All business operations are handled by one Node.js/Express backend application.
- The backend is started from `server.js` and is organized using the existing `routes`, `controller`, `middleware`, `model` and `config` layers.
- Business data lives in two stores, and only the backend connects to either of them:
  - **Supabase PostgreSQL** is the system of record for workflow state, allocation, audit and every rule that must hold atomically. All PostgreSQL work for one operation can share one database transaction.
  - **MongoDB Atlas** holds descriptive venue and equipment detail used for search, suitability warnings and display, and owns each venue's setup/turnaround times and calendar: tentative holds and operational blocks (T27). MongoDB writes never take part in a PostgreSQL transaction (sections 7.3 and 7.4).
- Supabase Auth provides identity. The backend remains the authority for application roles, relationships, workflow state and business-data writes.
- Business areas, including booking conflict detection and the operational safety check, are code modules inside the same backend process. Do not create independently deployed services, service-to-service APIs, further databases or message brokers unless a future approved architecture decision requires them.

The two repositories are a source-code ownership boundary, not a microservice boundary. The Next.js frontend is a client of the single backend monolith.

### 1.2 Architectural boundaries

| Boundary                     | Responsibility                                                                                                                                                                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Next.js pages and components | Presentation, navigation, form state, accessible feedback and calls to the backend                                                                                                                                                              |
| Backend routes               | Map HTTP requests to the correct controller and attach middleware; no business workflow logic                                                                                                                                                   |
| Backend controllers          | Validate and normalize request input, invoke model/domain operations and translate outcomes to safe responses                                                                                                                                   |
| Backend middleware           | Authentication, authorization context, request-level checks and shared request behavior                                                                                                                                                         |
| Backend models               | PostgreSQL and MongoDB access, domain state changes, transactional checks and persistence rules                                                                                                                                                 |
| Backend jobs                 | Scheduled internal work (expiry, completion, MongoDB sync, consistency monitoring) that calls model operations                                                                                                                                  |
| Backend configuration        | Construct external clients and read validated environment configuration                                                                                                                                                                         |

### 2.3 Backend placement rules

- `server.js` configures Express, shared middleware, route mounting, error handling, startup and shutdown. It must not contain feature SQL, MongoDB queries or workflow rules.
- `routes/*.js` declare route paths and middleware order. Route files must remain thin.
- `controller/*.js` deal with transport input and output. A controller must not trust actor IDs or roles supplied by the request body.
- `model/*.js` own database queries and domain changes. Cross-domain changes must share one PostgreSQL transaction/client rather than opening unrelated writes.
- `venueDetailModel.js`, `venueCalendarModel.js`, `venuePhotoModel.js` and `equipmentDetailModel.js` are the only files that query MongoDB. Every other model reaches MongoDB through them. They read and write documents and apply outbox entries; the rules that use the documents live in `venueConflictModel.js` and the domain models.
- `venueConflictModel.js` holds booking conflict detection: occupied-range calculation, overlap checks against bookings, holds and blocks, hold expiry, and the availability calendar. The set-once rule for setup/turnaround minutes is enforced in `venueModel.js` and in the `venueDetailModel.js` write. `safetyModel.js` holds the operational safety check. Both are modules, not services.
- The event venue section (T29) lives in `venueModel.js` and `venueController.js` and is mounted under `/api/events/:id` in `eventRoutes.js`; the suggestion is written atomically by the PostgreSQL function `suggest_event_venue`.
- `jobs/*.js` run scheduled internal work. A job claims work with a durable lease and calls model operations; it contains no business rules of its own. `jobs/runner.js` is started from `server.js` and exposes no HTTP trigger.
- `middleware/auth.js` verifies the Supabase access token and establishes the authenticated identity.
- `middleware/authorize.js` applies role and relationship policies after authentication. Hiding a frontend button is not authorization.
- `config/supabase.js` and `config/mongodb.js` read private server environment values and construct their clients once at startup. They must not export credentials to the frontend or log them.
- `supabase/migrations` is the only durable history for PostgreSQL schema changes, and `mongodb/migrations` (with `mongodb/schemas`) is the only durable history for MongoDB collections, validators and indexes. Do not make undocumented remote-only changes in the Supabase dashboard or the Atlas UI.
- Keep domain naming aligned across route, controller and model files so a feature can be traced vertically.

Do not introduce `src/modules`, `src/platform`, `src/workflows` or another competing backend root merely because an agent prefers that pattern. A major restructuring requires an approved ticket and coordinated README/master update.

#### 2.3.1 Backend code structure and writing style

The existing `healthModel.js`, `routers.js`, `authController.js` and `authRoutes.js` files are the coding-style reference for backend work. Unless an approved refactoring ticket changes the convention, agents must extend the backend in the same recognizable style rather than introducing a different JavaScript architecture.

Required conventions:

- Use CommonJS imports and exports: `require(...)` and `module.exports`. Do not mix in ES-module `import`/`export` syntax or TypeScript syntax.
- Use double quotes for strings and semicolons at statement boundaries.
- Use `const` by default and named `async` arrow functions for asynchronous model and controller operations.
- Keep the established route → controller → model flow. A route imports its controller, registers it on an Express `Router`, and exports the router. A controller awaits the model operation and sends the HTTP response. A model performs or delegates the data operation and returns domain data.
- Keep route files minimal. They may compose middleware and controllers, but must not contain database queries or workflow logic.
- Keep `req` and `res` inside controllers. Models must not depend on Express request or response objects.
- Use `try/catch` at the controller boundary, log enough server-side context for diagnosis, and return a safe client error without exposing credentials, SQL text or stack traces.
- Follow the indentation and spacing of the nearest existing file. Do not reformat unrelated files as part of a feature ticket.
- Use concise, feature-specific function names such as `getEvent`, `submitEvent` or `getVenueAvailability`. The existing `test` name is health-check boilerplate and is not a naming pattern for production handlers.
- Keep comments sparse and useful. Explain a non-obvious decision or invariant; do not narrate straightforward code or copy decorative comments mechanically.

Reference shapes:

```js
const express = require("express");
const router = express.Router();

const getEvent = require("../controller/eventController");

router.get("/:eventId", getEvent);

module.exports = router;
```

```js
const findEventById = require("../model/eventModel");

const getEvent = async (req, res) => {
  try {
    const event = await findEventById(req.params.eventId);
    res.status(200).json({ event });
  } catch (error) {
    console.error("Error:", error);
    res.status(500).json({ error: "Internal Server Error" });
  }
};

module.exports = getEvent;
```

These examples define code shape, not a complete endpoint or authorization implementation. Real controllers must apply the authentication, authorization, validation and business rules required by the ticket and this master.

Preserve the examples' style without copying weaknesses from boilerplate. In particular, models must not convert thrown failures into ordinary successful return values, generic placeholder names must not spread into domain code, and environment initialization should occur once at application startup rather than being added to every new controller. Correctness, security and transaction rules in this master take precedence when a sample is incomplete.

## 3. Product Scope and User Experience

ConnectSphere manages event requests from draft through coordinator assignment, review, resource planning, operational safety review, confirmation, preparation, attendee registration and completion. It also handles clarification, reassignment, tentative venue holds, multi-venue arrangements, venue unavailability and replacement, changes after planning has started, cancellation, resource incidents, notifications and audit history.

### 3.1 Roles

| Code               | Role                         | Main responsibility                                                                                                        |
| ------------------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `ORGANISER`        | Event Organiser (EO)         | Create event requests, answer clarifications, request changes and manage registration policy                               |
| `COORDINATOR_LEAD` | Event Coordinator Lead (ECL) | Review the shared unassigned queue, assign coordinators, and supervise and reassign the events they assigned               |
| `COORDINATOR`      | Event Coordinator (EC)       | Review assigned events, coordinate resources and make lifecycle decisions for assigned events                              |
| `VENUE_STAFF`      | Venue Staff (VS)             | Maintain venue data, setup and turnaround times and blocks; decide venue-booking requests; record venue preparation        |
| `TECH_SUPPORT`     | Technical Support Staff (TS) | Review technical needs, reserve equipment/support and record technical preparation                                         |
| `SAFETY_OFFICER`   | Safety Officer (SO)          | Conduct the Operational Safety Check and approve, reject or request changes to an event's arrangements                     |
| `ATTENDEE`         | Attendee (AT)                | View published events and manage personal participation                                                                    |

Users may hold multiple roles, and a multi-role user receives each role's permissions only within that role's scope. One exception applies: a user cannot hold both `COORDINATOR_LEAD` and `COORDINATOR`. A Lead supervises assignments but never acts as a coordinator, and cannot assign an event to themselves.

There is no System Administrator role. External users self-register as organiser or attendee only. Staff accounts and staff roles are created through trusted provisioning (system defaults or seed scripts). The Lead does not create, change or deactivate accounts. Before an internal user is deactivated, their active work must be moved: a coordinator's active events are reassigned, and a Lead's supervised events are handed to another Lead (section 5.8).

### 3.2 Included capabilities

- Authentication, profile provisioning, roles and organization membership.
- Draft event creation, submission, review, clarification (shown to users as "Returned"), resubmission, feasibility acceptance, operational safety review, confirmation, preparation, rejection and completion.
- A shared unassigned queue for submitted events, with one or more Event Coordinator Leads who assign coordinators and supervise the events they assigned.
- Venue catalogue, per-venue setup and turnaround times, availability, suitability, tentative holds with expiry, booking review, conflict prevention, operational blocks, booking restoration and per-booking preparation status.
- Multiple venue bookings for one event, each with its own time window and checked independently, with one primary venue shown to attendees.
- Equipment inventory, time-based availability, technical review, reservation and preparation status.
- Attendee registration, capacity enforcement, waiting list, offers, withdrawal and attendance history.
- Change requests, cancellation, venue replacement and resource incidents.
- Durable in-app notifications and audience-filtered activity history.

### 3.3 Baseline exclusions

Payments, pricing, full reporting/export suites, general document management, recurring or multi-session events, sub-divisible rooms within a venue, demographics, favorites and detailed staff rostering are outside the baseline. Multiple venues for one event are in scope (section 5.4.2); each venue remains one independently bookable space. A room that can be booked on its own is its own venue, linked to its hall for display through related venues (6.4, T31); booking a hall never blocks its rooms, or the reverse. The draft database diagrams may show fields or tables for excluded capabilities; those diagrams are reference material, not authority to implement them.

## 4. Authentication and Authorization

### 4.1 Authentication sequence

1. The frontend signs the user in through Supabase Auth.
2. The frontend sends the access token to the Express backend with authenticated business requests.
3. `middleware/auth.js` verifies the token's signature, issuer, expiry and audience using the supported Supabase verification mechanism.
4. The backend loads the active application profile, trusted roles and organization memberships.
5. The controller/model operation checks role, relationship, allowed fields and lifecycle state.

Do not trust a decoded-only token, a body-supplied actor ID, an `X-User-ID` header or user-editable metadata for permissions. Role switching in the UI changes presentation only; it cannot expand server permissions. The frontend takes the role from the backend profile through `useSessionUser`, never from an email address, display label or client-editable Auth metadata. On logout the frontend asks the backend to revoke the session, and protected content is rechecked when the page is restored from browser history.

### 4.3 Database and credential boundary

- The browser may communicate directly with Supabase Auth for session operations.
- Business reads and writes go through the Express backend. The browser never connects to PostgreSQL or MongoDB.
- The backend uses private server configuration and least-privilege database access.
- Developer Supabase and MongoDB MCP permissions are separate from the application's runtime identity and end-user permissions. The backend reads `MONGODB_URI`, never the MCP variable `MDB_MCP_CONNECTION_STRING`.
- The backend's only direct PostgreSQL connection is `VENUE_LOCK_DATABASE_URL` (section 2.7.2), used for venue calendar writes under the venue lock (section 7.4, T33). Its database role has least privilege. Every other business read and write goes through `config/supabase.js`.
- Database credentials, service-role keys, MongoDB connection strings and private MCP tokens must not enter frontend code, committed files, logs, Jira or chat output.
- Atlas access is limited by individual database users and the Network Access IP list, both managed by the team's Atlas admin.
- Use parameterized queries, explicit allowed origins, bounded request sizes and redacted errors/logs.
- Audit records are append-only for the application runtime.

If the project temporarily exposes tables through a Supabase Data API, row-level security and grants must prevent the browser from bypassing backend workflow rules. The preferred application boundary remains the Express backend.

### 5.2 Event lifecycle

Canonical states are:

`DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `AWAITING_CLARIFICATION`, `PLANNING`, `SAFETY_REVIEW`, `CONFIRMED`, `PREPARATION`, `COMPLETED`, `REJECTED`, `CANCELLED`.

The customer's names for these stages are: Draft → Submitted (unassigned queue) → Assigned / Under Review → Planning → Venue & Tech approved → Pending Safety Check → Confirmed → Preparation → Completed, with Returned, Rejected and Cancelled as separate outcomes. "Returned" is `AWAITING_CLARIFICATION`. "Venue & Tech approved" is a readiness condition inside `PLANNING`, not a stored state. There is no `APPROVED` state.

`SUBMITTED` always means "waiting in the unassigned queue": an event in `SUBMITTED` has no coordinator, and every active state from `UNDER_REVIEW` onward has exactly one.

```text
DRAFT ──submit──▶ SUBMITTED ──Lead assigns──▶ UNDER_REVIEW
UNDER_REVIEW ──request clarification──▶ AWAITING_CLARIFICATION ──resubmit──▶ UNDER_REVIEW
UNDER_REVIEW ──accept feasibility──▶ PLANNING ──submit for safety review──▶ SAFETY_REVIEW
SAFETY_REVIEW ──safety approved, coordinator confirms──▶ CONFIRMED ──start preparation──▶ PREPARATION
CONFIRMED or PREPARATION ──event end passes──▶ COMPLETED
SAFETY_REVIEW ──changes requested / rejected / superseded──▶ PLANNING
PLANNING … PREPARATION ──change accepted──▶ PLANNING              (sections 5.4.4, 5.7)
UNDER_REVIEW … SAFETY_REVIEW, never confirmed ──reject──▶ REJECTED
SUBMITTED ──organiser withdraws──▶ CANCELLED
Any active state after SUBMITTED ──cancel──▶ CANCELLED
```

| Start preparation        | Assigned EC                                         | `CONFIRMED`                                                                                                            | Enter `PREPARATION`; unlock preparation updates for Venue Staff and Technical Support; notify them                                                                                     |
| Complete                 | Internal job or assigned EC                         | `CONFIRMED` or `PREPARATION`; event end has passed                                                                     | Enter `COMPLETED` and close registration                                                                                                                                               |
| Reject                   | Assigned EC                                         | Never previously confirmed; `UNDER_REVIEW`, `AWAITING_CLARIFICATION`, `PLANNING` or `SAFETY_REVIEW`                    | Enter `REJECTED`; release holds, bookings and reservations; preserve history                                                                                                           |
| Accept change            | Assigned EC                                         | Open change request (section 5.7)                                                                                      | Update the requirements, invalidate safety approval, enter `PLANNING`                                                                                                                  |
| Withdraw                 | EO owner                                            | `SUBMITTED` (no coordinator yet)                                                                                       | Enter `CANCELLED`; remove from the queue; notify Leads                                                                                                                                 |
| Cancel                   | Assigned EC, directly or by approving an EO request | Active state after `SUBMITTED`; reason recorded                                                                        | Enter `CANCELLED`; release resources and close registrations/offers                                                                                                                    |

Submission requires title, purpose, start/end interval, positive expected attendance and venue/layout requirements. Submission does not assign a coordinator and never fails for lack of an available coordinator. An event without a coordinator cannot be reviewed, clarified, accepted, rejected or planned.

Clarification preserves all question/response rounds. Do not start new planning arrangements while clarification is outstanding. Ordinary comments cannot substitute for formal review steps.

After submission, ordinary descriptive/contact changes may be permitted. Date, duration, attendance, venue/layout and equipment changes are significant and must use the change workflow in section 5.7, except when explicitly amended during the clarification loop.

An organiser may provide optional technical-support needs with the event request (SPM-38, clarified by the user on 28 October 2026). These are requirements for the coordinator to review from submission onward, separate from formal technical arrangements. The owner may save them in a private draft and amend them during clarification; coordinators cannot change them through ordinary direct edits. The implementation stores `event.technical_support_needs` (up to 2,000 characters). Backend and frontend fixes are merged to main; migration `20261028120000_spm38_submitted_support_needs` was applied to shared development on 29 October 2026 and passed 12 hosted rollback smoke checks.

New holds, venue bookings and technical requests are created only while the event is in `PLANNING`. A venue replacement or accepted change returns the event to `PLANNING` first, so this rule has no exceptions.

`events.arrangement_version` increases in the same transaction whenever the event's active venue bookings, booking decisions, blocking incidents, technical arrangements or expected attendance change. A safety approval is valid only for the arrangement version it reviewed.

### 5.3 Readiness, preparation and publication

An event can be submitted for safety review when all of these hold, and confirmed when they still hold and the current safety round is approved:

- at least one active venue booking, and every active booking approved, suitable and free of conflicts over its occupied range ("Venue & Tech approved");
- exactly one active booking marked as the primary venue;
- approved equipment and support arrangements for every requested technical need, or `NOT_REQUIRED`;
- valid registration settings when registration is enabled, with registration capacity no greater than the primary venue's capacity;
- no open blocking incident and no open change request.

Holds, and rejected, expired, released or cancelled bookings, never count toward readiness. A booking that was rejected stays visible in the event's history; the coordinator replaces it or revises the plan. Coordinators cannot override a missing readiness item.

Preparation comes after confirmation. Venue Staff record preparation progress per venue booking, and Technical Support per technical request, only while the event is in `PREPARATION`. Event-level preparation progress is the aggregate of those records. Preparation progress does not block completion.

Attendee discovery is limited to events whose status is `CONFIRMED` or `PREPARATION` and that are published and have not ended (attendee lifecycle rule of 31 October 2026, superseding SPM-44's `CONFIRMED` only). `PREPARATION` comes after confirmation and stays attendee-facing. Events in any other state are not discoverable by attendees, in the list or by direct detail access. A new event defaults to unpublished; a successful confirmation publishes it, and no later transition unpublishes it (an event back in `PLANNING` is hidden by its status). Registration availability never hides a discoverable event. Attendees see the primary venue only; the organiser sees every venue. When a previously confirmed event returns to `PLANNING`, attendees continue to see the last confirmation snapshot, registration pauses, and attendees are notified only when the event is reconfirmed with changed attendee-facing details.

### 5.4 Venue rules

- The baseline treats each venue as one independently bookable space; the draft `Room` entity is not authoritative.
- Venue booking states are `PENDING`, `APPROVED`, `REJECTED`, `EXPIRED`, `RELEASED` and `CANCELLED`; `PENDING` and `APPROVED` are active and occupy the venue. A `PENDING` request is the venue's tentative hold until its `hold_expires_at` (section 5.4.3, version 1.14). `HOLD` entries in the MongoDB venue calendar placed before 1 November 2026 also occupy the venue until they expire.
- Capacity and booking-against-booking checks read PostgreSQL. Setup/turnaround minutes, active holds and blocks are read from MongoDB, under the per-venue lock that serialises every calendar write (sections 6.4 and 7.4); when MongoDB is unavailable, no hold, booking or block can be created and the calendar shows no availability. Layout, facility and accessibility information comes from MongoDB `venue_details`.
- Each booking is checked on its own requirements and its own booking window. Capacity against the booking's expected attendance, and availability over the booking's occupied range against active bookings, active holds and blocks, are blocking checks. Venue Staff see each pending or approved booking's checks before deciding, and the assigned coordinator sees them for each booking while preparing a request, as an advisory dry run that saves nothing (SPM-186); other bookings of the same event at other venues never affect a booking's result.
- Supported layout, required facilities, accessibility and operating hours produce warnings shown to the coordinator and Venue Staff; Venue Staff decide. The operating-hours check covers the whole occupied range, from setup start to turnaround end; any part outside the venue's hours produces a warning, not a block.
- Coordinators cannot override blocking checks or Venue Staff decisions. There are no staff overrides for venue conflicts.
- Venue search may return partial matches with suitability warnings (section 5.4.5). Search is advisory; the PostgreSQL recheck inside the decision transaction is authoritative.
- Time ranges are half-open: `[start, end)`. Adjacent ranges are allowed; any overlap, including one second, is a conflict. Competing requests are decided strictly first come, first served.
- Venue rejection releases the rejected booking but keeps the event in planning so an alternative can be selected. Other bookings for the same event are unaffected and stay attached.
- SPM-189 AC9: withdrawing an approved, not-yet-started booking returns a `CONFIRMED` or `PREPARATION` event to `PLANNING` through the guarded `venue_approval_withdrawn` transition. A `SAFETY_REVIEW` event returns through safety supersession. The event details, registrations, confirmation snapshots, other bookings and `previously_confirmed` flag are retained; the arrangement version increases once. This does not change the separate whole-venue out-of-service workflow.
- Venue Staff decide each booking on its own; there is no bulk decision (SPM-186). Approval rechecks, inside the decision transaction, that the booking is still `PENDING`, the event is in `PLANNING`, the venue is active and `ACTIVE`, the attendance fits and no other active booking (`PENDING` or `APPROVED`) overlaps the occupied range, using its stored range with a legacy fallback. A rejection needs a reason, which may suggest alternatives (SPM-189). The decision records who made it and when (`reviewed_by`, `reviewed_at`); a second decision made from a stale view is refused (`409 BOOKING_ALREADY_DECIDED`).
- Venue Staff may also reject an **approved** booking that has not started yet when the venue can no longer host it, for example because maintenance came up after approval (T32). The reason is required; the event is never cancelled or rejected, its original information is kept, its arrangement version increases, an open safety review is superseded (the event returns to `PLANNING`) and the coordinator and organiser are told, as in section 5.4.4. Changes on the day itself stay offline (5.4.4).
- Taking a whole venue out of service (status `INACTIVE` or `UNDER_MAINTENANCE`, section 6.2) while it has bookings ahead first warns Venue Staff with the affected events and asks them to confirm (SPM-73). On confirmation (T32) bookings and events are kept; in the same transaction each affected event's arrangement version increases, an open safety review is superseded, an organiser-safe history entry is written and the coordinator (with the reason), the organiser (without it) and the other Venue Staff are notified. The coordinator liaises with the organiser and replaces the venue, or restores the booking when the venue is active again. Until the `resource_incidents` table exists, no incident row is created for this, and readiness does not yet refuse an approved booking at a venue out of service.
- Edits to a venue's capacity, facilities or operating hours notify Venue Staff and the coordinators of affected future events for manual review; existing bookings are not recalculated automatically.

#### 5.4.1 Setup and turnaround time

- Venue Staff set `setupMinutes` and `turnaroundMinutes` for each venue in its MongoDB `venue_details` document, as non-negative whole minutes. Both are required when a venue is created (version 1.14). Zero is allowed, and each venue may have different values. There is no per-event override. A venue without these values cannot receive holds or bookings.
- A booking's occupied range is `[booking_start − setupMinutes, booking_end + turnaroundMinutes)`, computed from the venue's MongoDB minutes and stored with the hold or booking when it is created (on the PostgreSQL booking row, or in the hold document). Availability, suitability, conflict detection and the booking exclusion constraint use the occupied range, not the advertised booking time. For example, a booking from 10:00 to 12:00 at a venue with 30 minutes of setup and 45 minutes of turnaround occupies `[09:30, 12:45)`. Another booking's setup may start at 12:45; starting at 12:44 is a conflict.
- A multi-day event or booking occupies the venue as one continuous range, from the first day's start less setup to the last day's end plus turnaround, nights included (T30). A booking, hold or block on any of its days is a conflict; nights outside operating hours are a warning like any other operating-hours issue.
- Setup time and turnaround time are each set once, when they are still empty (usually when the venue is created); zero counts as set. After that they can never be changed, so existing bookings never change underneath an event. A request to change a recorded value is refused (`409 VENUE_BUFFERS_LOCKED`).
- Equipment reservations do not use venue buffers (section 5.5).

#### 5.4.2 Multiple venues for one event

- An event may have several active venue bookings, at most one per venue. Each booking carries its own label (for example "Main hall" or "Breakout A"), its own booking window, expected attendance, layout and required facilities/accessibility.
- A booking window must lie within the event's start and end. Suitability, availability, setup and turnaround are checked independently for each booking and its own window.
- Each booking's expected attendance must not exceed its venue's capacity.
- The coordinator designates exactly one active booking as the primary venue before confirmation. Attendees see only the primary venue; the organiser sees every venue with its status. Registration capacity cannot exceed the primary venue's capacity (section 5.6). Changing the primary venue rechecks the registration capacity.
- Every active booking must be approved before the event can be confirmed. If one venue is rejected, the event stays in planning while the coordinator arranges a replacement or revises the plan; approved bookings remain attached.
- Cancelling one venue booking does not cancel the others. Other bookings are released only by an explicit coordinator action, event rejection or event cancellation.

#### 5.4.3 Tentative holds

Since version 1.14 (developer decision of 1 November 2026) a booking request is the venue hold:

- When the assigned coordinator sends venue booking requests to Venue Staff (event in `PLANNING`), each `PENDING` request holds its venue over its occupied range, setup and turnaround included. No other event, coordinator or Venue Staff booking can overlap it (the no-overlap constraint, section 6.3). Operational blocks are still never refused (section 5.4.4).
- The hold expires (`venue_booking.hold_expires_at`, set when the request is saved) 7 days after it is sent, or 24 hours before its occupied range starts, whichever is earlier; a request sent within 24 hours of setup is held until setup starts. There is no extension; the coordinator sends a new request.
- Venue Staff approve the request (it becomes the approved booking and the expiry is cleared) or reject it (the venue is released). Approving a request whose hold has expired is refused (`BOOKING_HOLD_EXPIRED`).
- At expiry the request becomes `EXPIRED` and stops occupying the venue. `expire_overdue_venue_bookings` records this with a `STAFF_ONLY` history entry and notifies the coordinator; the booking request and approval paths run it for their venues under the venue lock first, and the hold expiry job runs it for every venue. Reads leave out an overdue request even before it is marked, so it never shows the venue as taken.
- The coordinator and Venue Staff are notified once, 24 hours before a request's hold expires (`remind_expiring_venue_bookings`, from the hold expiry job).
- Holds are handled by the backend only. Venue Staff see each pending request's "Respond by" time, and the coordinator sees until when the venue is kept; no role has a holds section, hold filter, hold count or hold label. The routes that request, place, decline and extend MongoDB holds are removed; holds placed before 1 November 2026 can still be listed, withdrawn and released, and expire as below.

The rules below applied to MongoDB holds before version 1.14 and still govern holds placed before 1 November 2026 until they expire.

- Venue Staff create a hold for an event in `PLANNING` at the coordinator's request. A hold is a `HOLD` entry in the MongoDB `venue_calendar` collection with a required `holdExpiresAt`; it is not a PostgreSQL booking. Holds apply to venues only, never to equipment.
- A hold expires 7 days after creation, or 24 hours before its occupied range starts, whichever is earlier. If the occupied range starts less than 24 hours from now, no hold is possible and the coordinator submits a booking request directly.
- Venue Staff may extend a hold once, at the coordinator's request and before it expires, by up to 7 more days, within the same 24-hours-before-setup limit.
- Active holds occupy the venue. Two events cannot hold overlapping occupied ranges at the same venue, and a hold cannot overlap an active booking or block.
- The coordinator converts a hold by confirming the held venue, which submits it as a booking request before expiry. A `PENDING` booking is created in PostgreSQL with the hold's occupied range and the hold becomes `CONVERTED`, so the slot is kept, and Venue Staff then approve or reject the booking. Implemented (SPM-188): the booking request names the hold (`holdId`) and keeps the hold's venue and window; under the event and venue locks, with database time, the hold must still be this event's, `ACTIVE` and unexpired. The hold is not counted against its own booking; the booking stores the hold in `venue_booking.calendar_hold_id` (unique, so one hold gives at most one booking) and the MongoDB hold becomes `CONVERTED` with `convertedBookingId` before COMMIT (T35; a lost COMMIT is repaired on the next attempt). Hold views show the linked booking's status. The expiry job takes the same locks and clock, so a hold is converted or expired, never both; a refused conversion saves nothing. A hold expiring within 24 hours shows the time left ("Hold expires in 6 hours"), and when another event's hold blocks a booking the coordinator is offered a different time, a different venue or the availability calendar, with guidance to contact Venue Staff.
- At expiry a hold becomes `EXPIRED`, the venue becomes available to other requests, and the hold can no longer be converted or extended. An expired hold is never treated as a booking. The event stays in `PLANNING`.
- A hold whose `holdExpiresAt` has passed is expired whatever its stored status: every check and the calendar treat it as expired at the time of reading, so an overdue hold never blocks the venue even if the expiry job has not run. Converting or extending an overdue hold fails. The job only records the `EXPIRED` status and sends the expiry notifications.
- The coordinator and Venue Staff are notified 24 hours before a hold expires (immediately, if the hold lasts less than 24 hours) and again when it expires.
- Hold reminder/expiry processing uses PostgreSQL time and the shared event → venue locks, re-reading the hold under the locks. A durable notice claim commits with history and notifications; version/expiry-guarded MongoDB progress is acknowledged after commit so retries recover safely and reminder batches advance.
- A hold is released when the event is rejected or cancelled, when the coordinator or Venue Staff release it, or when the booking is updated.
- A new hold lasts at most 7 days and ends at least 24 hours before setup starts. SPM-188, SPM-190 and SPM-279 are aligned to this cutoff (31 October 2026). The single extension still obeys the same setup cutoff.
- **Hold requests (T34).** The assigned coordinator asks for a hold in the app: one venue and one window inside the event, a label, optional expected attendance and a note of up to 500 characters. The request is a `venue_hold_request` row (section 6.2), `PENDING` until Venue Staff place the hold (`PLACED`, naming the calendar hold) or decline it with a reason of up to 1000 characters (`DECLINED`), or the coordinator withdraws it (`WITHDRAWN`). An event has at most one pending request per venue. Venue Staff see each pending request with the same per-window checks as a booking (capacity, availability, setup and turnaround, the 24-hour cutoff and when the hold would expire). Placing runs under the venue lock (section 7.4): PostgreSQL records the placement, then the MongoDB `HOLD` entry is written before commit, and the hold ID is derived from the `Idempotency-Key`, so a retry never places two holds. Extending and releasing lock the event and then the venue the same way; Venue Staff extend, and Venue Staff or the assigned coordinator release.

#### 5.4.4 Operational blocks, replacement and restoration

- Venue Staff create venue blocks with a reason (`MAINTENANCE`, `EQUIPMENT_FAILURE`, `RENOVATION`, `SAFETY`, `OTHER`), an interval and a note. A block is a `BLOCK` entry in the MongoDB `venue_calendar` collection. Blocks have no setup or turnaround time and are shown on the venue calendar.
- Creating a block is never refused because of existing bookings. Blocks are not part of the booking exclusion constraint; new holds and bookings are checked against active blocks under the venue lock before they are written (section 7.4).
- When a block is created, every active hold or booking whose occupied range overlaps the block receives a `VENUE_BLOCK` incident and the event's arrangement version increases. The coordinator and Venue Staff are notified, and the organiser is told that their venue arrangement is affected and what happens next. Attendees are not notified about an unresolved internal issue. The event is not cancelled or rejected automatically, the booking is not deleted, and the original event information is preserved.
- The event keeps its current state while the coordinator decides the next action. An open blocking incident prevents submission for safety review and confirmation. An open safety review on the event is closed as `SUPERSEDED` and the event returns to `PLANNING`.
- The coordinator's options are:
  1. **Restore the original booking.** If the block is lifted or shortened so that the venue is free for the booking's whole occupied range, Venue Staff confirm the restoration. The incident is resolved and the event keeps its state.
  2. **Replace the venue.** The coordinator raises a venue replacement, which is recorded as a change request (section 5.7). The event enters `PLANNING`, and the new venue request goes through the full hold/booking approval, then safety review and confirmation again. The affected booking is released when the replacement is approved, or earlier if the coordinator releases it. If the original venue becomes free before the replacement is approved, option 1 remains available and the replacement request can be withdrawn.
  3. **Cancel the event**, under the normal cancellation rules, if no alternative can be found.
- Moving an event on the day it takes place is coordinated by staff offline and then recorded in the system.
- A block covers a set period and creates incidents. Taking a whole venue out of service (status `INACTIVE` or `UNDER_MAINTENANCE`, section 6.2) is a separate action: it alerts the affected events but creates no incidents. Both increase the affected events' arrangement versions and supersede an open safety review (T33).

#### 5.4.5 Venue search and calendar data

- Search runs in two steps. First, `venueDetailModel.js` filters `venue_details` on required layout, facilities and accessibility to produce candidate IDs and warnings. Second, `venueModel.js` checks those candidates in PostgreSQL for active state, capacity and operating hours, and `venueConflictModel.js` checks availability over the occupied range against PostgreSQL bookings and MongoDB holds and blocks. Results combine blocking failures and warnings.
- When MongoDB is unavailable, search returns PostgreSQL-only results with layout, facility and accessibility marked "not checked" (M4), and availability is reported as unknown, never as available.
- The layout, facility and accessibility filters each take up to 10 values (repeated query parameters; one value still works). A venue matches a filter when it has any of its values, case-insensitively, and must match every filter used (T31). Without MongoDB, layout and accessibility fall back to the PostgreSQL room layouts and accessibility note, and the facility filter is reported as not checked. Required facilities (`requiredFacilities`) still rank and highlight venues on the API, but the coordinator's search no longer offers them.
- **Capacity suitability (SPM-198).** In the event's venue section, the capacity requirement of each venue also carries an assessment against the event's expected attendance: more places than expected guests is **Capacity Sufficient** ("Venue capacity is adequate (200 seats for 150 guests). Comfortable spacing available."); exactly as many is **Capacity Adequate** ("Venue exactly meets expected attendance (150 seats for 150 guests). No buffer space. May feel crowded."), still met but shown amber; fewer is **Capacity Insufficient** ("Venue is too small (100 seats for 150 expected guests). Cannot accommodate. Recommend alternative venue."), unmet. An insufficient venue's details offer **Find Alternative Venues**, which opens the venue search filtered to venues whose capacity is at least the expected attendance. Without an expected attendance there is no capacity requirement and no assessment. The wording is the backend's (`venueModel.venueRequirements`); the frontend does not work it out.
- Related venues (`venue_details.relatedVenueIds`, 6.4) are display-only: the venue section lists those still active and in service, by name, and never uses them in a check.
- In the coordinator's calendar the checked request is drawn on the timeline: a translucent yellow block labelled with the request ID and times (details on hover), red where its occupied range overlaps an existing booking, hold or block, and grey for hours outside every shown venue's operating hours; month view shows entries as labelled bars and year view tints busy and requested days. The calendar shows no summary cards.
- The venue availability calendar merges PostgreSQL bookings (`PENDING` and `APPROVED`) with MongoDB holds and blocks, using each venue's MongoDB setup/turnaround minutes for bookings. It distinguishes available periods, bookings, active holds (with expiry), blocks (with reason and note) and operating-hours warnings. If MongoDB cannot be read, the calendar returns an error rather than showing any period as available.

### 5.5 Equipment and technical-support rules

- Inventory total is not the same as interval availability.
- Availability equals total usable stock in usable condition minus active reservations and applicable unavailability during every segment of the requested interval.
- Reservations use the event interval. Venue setup and turnaround time does not apply to equipment, and equipment transit time between venues is zero.
- Equipment location is reference information that helps Technical Support plan delivery. It never reserves or blocks a venue and is not part of the availability calculation.
- A technical request is fulfilled completely or rejected; partial approval is not allowed. All lines in one technical approval succeed and reserve atomically or all fail.
- Damaged or maintenance stock is represented explicitly and is not double-counted.
- Quantities, unavailability and reservations live in PostgreSQL. Equipment specifications live in MongoDB `equipment_details` and are display information only.
- Support-only requests still require technical review when on-site support is requested.
- Resource approval does not confirm the event. The event must still pass the safety review, and the assigned coordinator performs final confirmation.

### 5.6 Registration and waiting-list rules

- Registration is available for a confirmed attendee-visible event from the organiser-defined registration start time until the organiser-defined registration end time, subject to venue capacity. Once capacity is reached, direct registration stops and the separate waitlist flow applies (team rule of 30 October 2026, SPM-134). The organiser's registration-enabled flag is stored but is not an attendee eligibility gate.
- Registration requires a published event whose status is `CONFIRMED` or `PREPARATION`, the same events attendee discovery shows (5.3), database time inside its registration period `[registration_open_at, registration_close_at)`, a place left under the venue capacity and an active user. `PREPARATION` follows exactly the same registration, waitlist and offer rules as `CONFIRMED` (attendee lifecycle rule of 31 October 2026). Every event in any other state is hidden from attendees and refused as not found, so registration never reveals a hidden event's existence or state (SPM-134). A previously confirmed event that goes back to `PLANNING` or `SAFETY_REVIEW` is hidden in the same way until it is reconfirmed; existing registrations are retained.
- Registration availability, decided by database time by one database function (`event_registration_availability`) that Event Discovery shows and registration applies under the event lock (SPM-134): `NOT_YET_OPEN` before `registration_open_at`; `CLOSED` at or after `registration_close_at`, and for every status but `CONFIRMED` and `PREPARATION`; `FULL_WAITLIST` when registered places, active invitation holds and eligible queued attendees leave no place for direct registration during the registration period; `UNAVAILABLE` when the start time, end time or primary venue is missing, because missing data never means always open or unlimited; otherwise `OPEN`. The capacity is the primary venue's `max_capacity`, lowered by `registration_capacity` when the organiser set one. `is_registration_enabled` does not change availability, and there is no `NOT_ENABLED` state. A full event is never reported as `CLOSED`. Only `OPEN` accepts a direct registration; each refusal returns its own conflict code (`REGISTRATION_NOT_YET_OPEN`, `REGISTRATION_CLOSED`, `REGISTRATION_FULL`, `REGISTRATION_UNAVAILABLE`, `ALREADY_REGISTERED`, `ALREADY_WAITLISTED`). `FULL_WAITLIST` only reports that direct registration is full; joining the waitlist is a separate ticket. The frontend shows the backend's state and never recalculates it.
- A registration stores the dietary restrictions and accessibility requirements the attendee submitted for that event. The form starts from the attendee profile, but registering never changes the profile, and a later profile edit never changes a registration. Name and email stay on the user record.
- **Approved registration scope (SPM-134, 31 October 2026):** organiser-configured fields are excluded; only dietary restrictions and accessibility requirements are editable answers. Name and email remain read-only account information. Confirmations are transactional in-app notices under M5; no email or SMS provider is required. Jira AC6, AC11 and AC14 were reconciled to these decisions. Active waitlist offers and eligible queue priority remain protected by the registration capacity and deadline checks; the hosted correction and prior execution evidence are recorded in the SPM-134 test plans.
- Registration capacity cannot exceed the capacity of the primary venue. For example, with a 500-seat primary hall and two breakout rooms of 60 and 80, registration is capped at 500; the breakout rooms are sized by their own expected attendance.
- Each attendee has one registration record per event. A withdrawn attendee may re-enter only under the agreed policy and receives a new queue position.
- Capacity changes, registration, withdrawal, offer acceptance and invitation allocation lock the event and recheck capacity. Capacity cannot be reduced below confirmed registrations plus active invitation holds.
- When capacity is full, eligible users join a FIFO waitlist. Until the waitlist ticket (SPM-163) is built, a full event refuses direct registration with `REGISTRATION_FULL` and creates no waitlist record.
- An invitation reserves a place until accepted, declined, expired or cancelled.
- Accepting an expired invitation cannot consume capacity even if the expiry job has not yet run.
- Withdrawal or expiry may invite the next eligible waiting attendee in the same transaction.
- Attendees can view only their own registration, invitation and queue information.

### 5.7 Changes and cancellation

A change request is either an organiser change (date, duration, attendance, venue/layout or equipment requirements) or a venue replacement raised by the coordinator (section 5.4.4).

1. The organiser submits a change request with the proposed values and a reason; current details are not changed yet. An event has at most one open change request.
2. The assigned coordinator reviews it and accepts or rejects it, with a reason.
3. On rejection, nothing changes.
4. On acceptance, one transaction updates the event's requirements, increases the arrangement version, invalidates any safety approval and moves the event to `PLANNING`. Existing venue bookings and technical arrangements are **not** reset automatically; the coordinator reviews them and decides which to keep, revise, replace or release. New or revised requests go through Venue Staff and Technical Support approval as usual, then the event goes through safety review and confirmation again.
5. While the event is back in planning, attendees see the last confirmation snapshot and are notified only when the event is reconfirmed with changed attendee-facing details.

The Event Organiser may request cancellation at any time; the assigned coordinator approves or rejects the request. While the event is still in the unassigned queue, the organiser withdraws it directly. The assigned coordinator may also cancel an event directly with a recorded reason. Cancellation releases active holds, venue bookings and equipment commitments, closes registrations and offers, closes open change requests and safety reviews, records history and notifies the organiser, relevant staff and affected registered or waitlisted attendees. A never-confirmed request may be rejected; a previously confirmed event must use cancellation rather than rejection.

### 5.8 Coordinator assignment and Lead supervision

- Submitted events enter one shared unassigned queue, ordered oldest first, visible to every Lead. Events are never assigned automatically.
- Any Lead may assign a queued event to exactly one active coordinator. The assigning Lead becomes the event's **supervising Lead**. An event has at most one coordinator and one supervising Lead at any time.
- A Lead sees the unassigned queue and the active events they supervise. Only the supervising Lead can reassign an event, in any non-terminal state after `SUBMITTED`.
- A Lead never acts as a coordinator: a user cannot hold both roles, and a Lead cannot assign an event to themselves or make lifecycle decisions.
- A coordinator cannot hand an event over directly. They request a transfer, with a reason, which notifies the supervising Lead; the Lead decides and performs any reassignment.
- On reassignment, all event-linked records (pending venue and equipment requests, holds, comments and history) stay with the event and become available to the new coordinator.
- A Lead may hand some or all of their supervised events to another Lead, for example before leave. The receiving Lead becomes the supervising Lead, and both are notified. Every supervision change is recorded.
- Before deactivation, a coordinator's active events must be reassigned, and a Lead's supervised active events must be handed to another Lead. The backend refuses to deactivate a user who still holds active work.
- Resubmission after clarification returns the event to its existing coordinator, not to the unassigned queue.
- Assignment notifies the new coordinator and the organiser. Reassignment notifies the new coordinator, the previous coordinator and the organiser.
- Events assigned before v0.8 keep their coordinators. They have no supervising Lead and appear to every Lead under "Unsupervised" until a Lead takes over supervision.

### 5.9 Operational safety check

- The assigned coordinator submits an event for safety review from `PLANNING` once the readiness conditions in section 5.3 hold, apart from safety approval. An event without technical needs can be submitted once all its venue bookings are approved.
- Open reviews form a shared queue. Any active Safety Officer may claim one; each review round has one claimant, who is recorded. A Safety Officer sees only events in the queue or claimed by them, with the details and change history the review needs (attendance, venues and layout, access and equipment changes). They see attendance counts but not participant personal data.
- The review is a structured checklist with one entry per factor: attendance and capacity, layout, emergency access, accessibility, equipment placement and known venue restrictions. Each entry records a result and a comment. Emergency-access information and known restrictions are read from `venue_details`; if MongoDB is unavailable, the review cannot be decided until the detail can be read.
- Each round ends with one outcome:
  - `APPROVED`: the coordinator may confirm the event.
  - `CHANGES_REQUESTED`: the event returns to `PLANNING` with the requested changes listed.
  - `REJECTED`: the safety arrangement is rejected for named venue booking(s), meaning those venues are unsuitable for this event as arranged. The event returns to `PLANNING` with the issue and reason visible to the coordinator; the event itself is not rejected.
- After `CHANGES_REQUESTED` or `REJECTED`, nothing is reset automatically. The coordinator decides what to revise or replace; revised requests go through normal approval, followed by another safety review. Rejecting or cancelling the event remains a separate coordinator decision.
- Each round stores organiser-visible comments separately from internal notes. The organiser sees the outcome and the organiser-visible comments; staff on the event see both.
- The Safety Officer always gives a response; there is no review timeout.
- Any change to the event's venue bookings, technical arrangements or expected attendance invalidates a safety approval. An open review whose arrangement version is no longer current is closed as `SUPERSEDED` and the event returns to `PLANNING`.
- All review rounds are preserved.

## 6. Data Ownership and Persistence

The supplied database and UML diagrams are design references and may contain errors. Use the following catalogues and actual verified migrations as the working data baseline. Never generate migrations or collections solely by copying a draft diagram.

PostgreSQL is the system of record for workflow state, bookings and audit. MongoDB owns descriptive venue and equipment detail, venue setup/turnaround times and the venue calendar of holds and blocks (T27). ### 6.1 Storage conventions

In PostgreSQL, use UUID primary keys, `timestamptz` instants and positive integer versions for mutable aggregates. Auth owns passwords; the application profile ID links to the Auth user. Draft-only mandatory fields may be null; submitted events require their mandatory data, while the coordinator stays null until a Lead assigns one.

Status and state columns use `text` with check constraints, not PostgreSQL enum types, so that lifecycle changes remain small migrations.

Retain events, bookings, requests, registrations, assignments, safety reviews and activity after closure. Restrict deletion of referenced business records. Do not cascade deletion of an Auth account into event or audit history. JSON requirement/plan/checklist fields require bounded documented schemas and cannot replace foreign keys or allocation constraints.

## 7. Transactions and Concurrency

Use one checked-out PostgreSQL client for `BEGIN`, every related query, `COMMIT` and `ROLLBACK`. Separate client/pool calls do not form one transaction. Cross-domain work stays in the single monolith and shares the same transaction context. MongoDB is never written inside that transaction (section 7.3).

Use an explicit lock order: event IDs, then venue IDs, then equipment IDs, each in stable order. The venue lock also serialises venue calendar writes across PostgreSQL and MongoDB (section 7.4). Operations that start from a venue, such as block creation, first read the affected event IDs, then acquire locks in the standard order and re-read the affected set; if the set has changed, the operation restarts. Scarce-resource operations should use appropriate isolation and bounded retry for serialization/deadlock failures. A retry must re-run every validation; a genuine resource conflict returns a business conflict instead of being retried blindly.

### 7.2 Interval and equipment calculation

All scheduling uses half-open intervals. Venue availability and conflicts use each booking's occupied range: `[booking_start − setupMinutes, booking_end + turnaroundMinutes)`, using the minutes stored on the booking or hold when it was created (section 5.4.1).

Equipment uses the event interval without venue buffers. For equipment, split the request interval at reservation and unavailability start/end points. For each segment calculate total stock minus active reserved quantity minus unavailable quantity. The minimum across all segments is the available amount.

For example, stock is five; one reservation uses three from 09:00–10:00 and another uses three from 10:00–11:00. A 09:00–11:00 request can reserve two because the existing reservations do not overlap. Subtracting both as six across the whole interval is incorrect.

### 7.3 Applying MongoDB writes

1. The operation's PostgreSQL transaction writes its own changes and an `outbox_entries` row, then commits.
2. After commit, the request handler attempts to apply the entry once through the detail model. The response does not wait for or depend on that attempt beyond reporting whether the detail is current.
3. `jobs/mongoSyncJob.js` claims unapplied entries with a lease, applies them with the conditional update in section 6.5 and retries failures with backoff.
4. An entry that keeps failing is marked failed after a bounded number of attempts, logged without credentials and surfaced to the developer through consistency monitoring. It is never deleted silently.

| Failure                                                       | Behavior                                                                                                                                                                                                 |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MongoDB unavailable after commit                              | PostgreSQL changes stand; the entry is retried; reads flag the detail as possibly out of date                                                                                                            |
| Entry applied twice or out of order                           | The version condition ignores the stale or repeated write                                                                                                                                                |
| MongoDB unavailable during venue search or a booking decision | Search results come from PostgreSQL only; layout, facility and accessibility warnings show as "not checked" (M4). Hold, booking, block and setup/turnaround writes and the calendar refuse (section 7.4) |
| PostgreSQL transaction rolls back                             | No outbox entry exists, so MongoDB is never touched                                                                                                                                                      |

### 7.4 Venue calendar writes (T27)

Holds, blocks and setup/turnaround minutes live in MongoDB, while bookings live in PostgreSQL, so no single database transaction covers them. The customer requires that overlaps are prevented outright and that simultaneous requests are decided strictly first come, first served (Week 1 briefing; Week 4 Booking Conflict Detection; Sessions 1–3). A known window in which two overlapping arrangements could both succeed is therefore not acceptable. Every venue calendar write follows this protocol:

1. **One lock per venue, in PostgreSQL.** Every operation that changes a venue's calendar opens a PostgreSQL transaction and locks that venue's row (`SELECT … FROM venue WHERE venue_id = $1 FOR UPDATE`) before reading anything. This covers booking creation and replacement, booking approval (SPM-186), hold create/extend/release/convert, block create/lift/shorten and setup/turnaround changes. The lock is held until the transaction commits or rolls back, so operations on the same venue run one after another and each sees the result of the one before. Use a short `lock_timeout`; a timeout returns a retryable conflict (`409`). The backend opens this transaction on the `VENUE_LOCK_DATABASE_URL` connection (section 2.7.2, T33), because supabase-js cannot hold a transaction across a MongoDB call.
2. **Checks under the lock read both stores.** A new or extended hold or a new booking is refused if its occupied range overlaps an active booking (PostgreSQL) or an active, unexpired hold or active block (MongoDB). Converting a hold ignores that event's own hold. The PostgreSQL exclusion constraint remains a second guard between bookings.
3. **Writes under the lock.**
   - _Hold create/extend/release:_ write the `venue_calendar` document and increase `venue_details.version` in one MongoDB transaction; write the activity record in the PostgreSQL transaction; commit.
   - _Booking (including conversion):_ insert the booking, arrangement version, activity and notification; when the booking confirms a hold, link it (`venue_booking.calendar_hold_id`) and mark the hold `CONVERTED` in MongoDB before COMMIT with a token-guarded undo, as for hold placement and blocks (T35). A refused COMMIT undoes the conversion. A lost COMMIT may have landed, so nothing is undone; the retry, under the same locks, finds a `CONVERTED` hold that no booking names, restores it to `ACTIVE` and converts it again.
   - _Block create/lift:_ write the incidents, arrangement versions, activity and notifications in the PostgreSQL transaction; write the `BLOCK` document in MongoDB; commit only if the MongoDB write succeeded, otherwise roll back. If the commit fails after the MongoDB write, the block stays and the consistency monitor creates the missing incidents.
   - _Setup/turnaround change:_ only editable once.
4. **All writes go through the backend.** The lock only works because nothing writes holds, blocks or setup/turnaround minutes any other way. Direct edits in Atlas or through MCP tools are forbidden (section 10.3.2).
5. **`venue_details.version`** continues to reject stale detail edits (`409`), for example when two Venue Staff edit the same venue from old copies.
6. **MongoDB unavailable.** No hold, block, booking or setup/turnaround edit can be made, and the calendar returns an error instead of availability. Refusing is the safer failure: a booking made without checking holds and blocks could double-book the venue.
7. **Lock order.** The venue lock follows the standard order in section 7 (events, then venues, then equipment). An operation that needs several venues locks them in ascending ID order.

## 8. Notifications and Internal Work

Notification and recipient rows are durable data written in the originating business transaction. They are the source of truth and the in-app inbox reads them. Network failure after commit does not remove them. The frontend refreshes after relevant actions/focus and may poll while active. There is no guaranteed instant-delivery SLA in the baseline.

Notifications are in-app only (M5). There is no email or SMS delivery in Release 1. Wording is audience-safe: each recipient sees only what their role may see.

| Trigger                                           | Required audience behavior                                                                                                                                |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Submission or withdrawal from the queue           | Notify owner and every Event Coordinator Lead                                                                                                             |
| Assignment                                        | Notify the new coordinator and the owner                                                                                                                  |
| Reassignment                                      | Notify the new coordinator, the previous coordinator and the owner; the previous coordinator loses mutation rights                                        |
| Transfer request or Lead handover                 | Notify the supervising Lead (transfer request) or both Leads (handover)                                                                                   |
| Clarification, response, feasibility or rejection | Notify owner/coordinator with role-appropriate wording                                                                                                    |
| Venue or technical decision                       | Notify responsible queue/staff, coordinator and safe owner summary. A venue rejection's reason goes to the coordinator only; the owner is told the venue could not be booked (or, for a withdrawn approval, that it is no longer available and the event is not cancelled)                                                                                        |
| Hold reminder or expiry                           | Notify coordinator and Venue Staff 24 hours before expiry and at expiry                                                                                   |
| Hold requested, placed, declined, extended or released (T34) | Notify Venue Staff of a new request; notify the coordinator when the hold is placed (with its expiry), declined (with the reason), extended (with the new expiry) or released by Venue Staff; nothing to the owner or attendees |

Use a unique originating action key to prevent duplicate notifications. Notification possession never restores access to an event after permissions change.

Internal work such as waitlist-offer expiry, hold reminders and expiry, completion of events whose end has passed, MongoDB sync, registration-window reconciliation and consistency monitoring (including blocks without incidents and holds left active after conversion, section 7.4) stays inside the backend repository. It must use database time, durable claiming/leases and bounded batches so restarts or multiple processes cannot duplicate work. Correctness cannot rely on a browser being open or an in-memory timer; for holds, treating an overdue hold as expired at read time (section 5.4.3) guarantees correctness even when the job is late. There are no public maintenance-job triggers.

Implement the ticket and its necessary supporting changes only: do not overwrite shared layouts, discard others' work or import unrelated pending features to make tests pass. 10. Run the real repository's lint/test/build commands and the relevant role journeys (section 11). For UI changes, check desktop and mobile placement and capture both. 11. Update the README if setup, scripts, environment variables or actual structure changed. Update this master if an enduring architecture or business rule changed.

Requiring that status check and review, and blocking direct pushes to main, are repository-owner settings.

If Jira acceptance criteria or linked tests are inaccessible, report the exact gap. Do not invent them and do not mark the ticket complete based only on assumptions in this document.

### 9.3 Compatibility between repositories

Coordinate related frontend and backend work with the same Jira issue. Agree the URL, permitted roles and request/response contract before parallel work starts. Do not rename an API property, workflow status or route in one repository alone; document the agreed change and link the corresponding PR in the other repository. Prefer additive backend changes while the frontend adopts them. Do not remove behavior still used by the other repository. Test mocks must remain clearly distinguishable from live integration and must be updated when the implemented backend behavior changes.

### 12.2 Change procedure

For an accepted customer change:

1. Record the request, decision and acceptance criteria in Jira.
2. Identify affected roles, lifecycle states, business rules, tables/constraints, notifications, frontend pages and both repositories.
3. Update the active sections of this master in place. Remove superseded instructions rather than leaving contradictory rules.
4. Update implementation, migrations, READMEs and tests together where applicable.
5. State whether the change is proposed, accepted or implemented. Implemented changes require code/database identifiers and actual verification evidence.
6. After 1.0, a change to a business rule increases the minor version (1.1, 1.2 …) and is summarised for the team in the changelog.

If this master, Jira, a repository README and implemented code disagree, surface the conflict. Jira controls the ticket's accepted behavior; this master controls enduring architecture/business intent; the code and migrations show current implementation; the README controls runnable repository setup. A design reference (section 10.5) controls visual presentation only. Do not silently select whichever source is easiest.
