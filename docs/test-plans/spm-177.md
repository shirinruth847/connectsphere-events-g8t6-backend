## Deployment and rollback

`supabase/migrations/20261020090000_spm177_lead_only_assignment.sql` is a
corrective migration after the existing assignment/history migrations. It
restores the active Lead check, retains the Coordinator lock/overlap check,
drops the obsolete two-argument function without CASCADE and returns the
Coordinator's display name in the assignment result. It updates no business
rows. Historical migrations remain unchanged.

It has NOT been applied to shared development. Inspect target migration
history and dependencies before an authorized deployment; the PR also contains
older, unapplied migration timestamps. Do not run a blanket historical push.
Preserve the current schedule guard and supervision/reassignment fixes on main
when integration is explicitly authorized. Deploy the reviewed final database
function before enabling its corresponding workflow application deployment.

Rollback requires an explicitly reviewed migration restoring the previous
Lead-only definition. Do not restore the permissive Coordinator policy or the
legacy overload. Application rollback alone does not restore SQL privileges.
No automatic assignment, event cleanup or supervisor backfill is performed.

## Verification boundaries

From the backend worktree:

```sh
npm ci --ignore-scripts
npm test -- --runInBand
PGLITE_MODULE=/path/to/@electric-sql/pglite node --test tests/database/*.test.cjs
```

The SQL suite uses a reduced fixture reused from the existing SPM-36 isolated
schema and an in-memory PGlite engine. It does not load the complete hosted
schema, reproduce production RLS or test concurrent PostgreSQL clients. It
never reads private environment variables or connects to Supabase.

Hosted tests still need a separately authorized environment, namespaced
synthetic fixtures and cleanup. Required cases include two separate clients
assigning overlapping events to one Coordinator, one assignment racing a
reassignment, actual function grants/RLS and confirmation of both notification
recipients through the application. Do not infer these results from mocks.

The frontend removes its stub `/assignments` page from this ticket's diff;
SPM-180's working page on main must be retained at the eventual authorized
integration. That integration and its conflicts remain deferred by the user.
