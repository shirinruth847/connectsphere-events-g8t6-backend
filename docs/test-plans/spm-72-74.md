# SPM-72 and SPM-74: venues inside the event request

Revised acceptance criteria and test cases for SPM-72 (View Venue Catalogue)
and SPM-74 (View Venue Availability), written in each ticket's existing Jira
format. They replace the ticket text from 23 October 2026 (developer brief:
coordinators browse, compare and select venues inside each event request; the
`/venues` page is removed for Event Coordinators and Leads). Implemented on
backend and frontend `feature/SPM-72-74-coordinators-venue`; Master 1.4, T29.

---

## SPM-72 — Venues in the Event Request

As an Event Coordinator, I want to browse, compare and select venues inside each event request so that I can choose the venue that best fits the event's requirements.

ACs:

* AC1 — Access: the assigned Event Coordinator browses venues in the Venue section of the event request page. The separate Venue Catalogue page (`/venues`) is no longer available to Event Coordinators or Event Coordinator Leads. Organisers, Venue Staff, Technical Support and Attendees cannot open an event's venue options; a coordinator who is not assigned to the event is told the event is not found.
* AC2 — Coordinator Lead: the Lead who supervises the event (made its current assignment) can open the event read-only and search, filter, sort, view and compare its venues, but cannot select a venue. The Lead does not review the coordinator's selection.
* AC3 — Search, filter and sort: the coordinator can search by venue name or location; filter by minimum capacity, layout, facility and accessibility; enter required facilities; and sort by best match, name, capacity, setup time or turnaround time, ascending or descending. When no venue matches, the system says so and offers to clear the filters. Invalid values (e.g. capacity 0) show an error against the field.
* AC4 — Venue details (read-only): each venue shows its photos, name, address, capacity, operating hours, setup time, turnaround time, rooms, supported layouts, facilities, accessibility features, emergency access, known restrictions and description. Nothing can be edited. Only venues that are active and in service are shown; deactivated, inactive and under-maintenance venues are never listed or selectable.
* AC5 — Ranking and highlighting: venues meeting every requirement of the request (capacity for the expected attendance, availability on the event date, preferred layout, each accessibility need and each required facility) are listed first, followed by venues with the fewest unmet requirements. Requirements that are met are highlighted in light green; unmet requirements are shown in light grey.
* AC6 — Availability for the event date: each venue shows whether it is available for the event's date and time, including its setup and turnaround time, and lists any booking, hold or block that overlaps. An operating-hours issue is a warning, not a block. The event's own bookings and holds never make a venue unavailable. When availability cannot be checked, the venue is shown as "Availability not checked", never as available.
* AC7 — Comparison: a toggle button opens a second panel so two venues can be compared side by side. The second panel is hidden by default and can be closed again.
* AC8 — Selection: while the event is Under Review or in Planning, the coordinator can select one venue after confirming. The selection is saved as the coordinator's suggested venue, recorded in the event's activity history and sent to the Organiser as a notification. It does not hold or book the venue. A venue that cannot hold the expected attendance cannot be selected. Selecting another venue replaces the suggestion.
* AC9 — Organiser view: the Organiser sees the suggested venue (name, address, capacity, who suggested it and when) on their event request, stated as not yet booked.
* AC10 — Integrity: a double-click or resubmission records one suggestion and sends one notification. If the suggestion was changed elsewhere, or the venue stopped being available, the system explains why, changes nothing and offers a reload. A failed save keeps the page as it was.
* AC11 — Empty and failure states: if no venues are available, the system informs the coordinator. If venue details cannot be loaded, layout, facility and accessibility requirements show as "not checked". If the venue list cannot be loaded, an error with a retry is shown.

Test Cases:

TC-VC-001 — View available venues in the event request

Test Scenario: Event Coordinator views the venues for an assigned event

Pre-conditions:

Event Coordinator is authenticated and assigned to the event.  
At least two venues exist and are available.

Test Steps:

Open the event request > Venue & layout section.  
View the list of venues.

Test Data:  
Venue A, Venue B

Expected Result:  
Venue A and Venue B are displayed with their photo, name, address, capacity, setup/turnaround time, availability and requirement highlights. No `/venues` catalogue link is shown.

TC-VC-002 — No available venues

Test Scenario: No venues are available for consideration

Pre-conditions:

Event Coordinator is authenticated and assigned to the event.  
No available venues exist.

Test Steps:

Open the event request > Venue & layout section.

Test Data:  
No available venues.

Expected Result:  
The system displays "No venues are currently available".

TC-VC-003 — Inactive venue not listed

Test Scenario: Deactivated, inactive or under-maintenance venues are not usable

Pre-conditions:

Venue A has been deactivated or set Inactive.  
Venue B remains available.  
Event Coordinator is authenticated and assigned to the event.

Open the event request > Venue & layout section.

Test Data:

Expected Result:

TC-VC-004 — Search, filter and sort

Test Scenario: Coordinator narrows and orders the venues

Pre-conditions:

Event Coordinator is authenticated and assigned to the event.  
Venues of different capacities and names exist.

Test Steps:

Enter "Hall" in Search and 200 in Minimum capacity; apply filters.  
Sort by Capacity, then switch to descending.  
Enter a filter that matches nothing.

Test Data:  
Search = Hall; Minimum capacity = 200; Minimum capacity = 0 (invalid)

Expected Result:  
Only matching venues with capacity of at least 200 are shown, ordered by capacity in the chosen direction. With no match, "No venues match these filters" is shown with Clear filters. Capacity 0 shows a field error.

TC-VC-005 — Requirement ranking and highlighting

Test Scenario: Venues meeting every requirement come first

Pre-conditions:

The event expects 150 attendees, prefers a Theatre layout and needs wheelchair access.  
Venue A meets every requirement; Venue B holds only 80.

Test Steps:

Open the Venue section; enter "Projector" as a required facility.

Test Data:  
Venue A (300, Theatre, wheelchair access, projector); Venue B (80)

Expected Result:  
Venue A is listed before Venue B and marked "Meets every requirement"; its requirements are light green. Venue B's capacity requirement is light grey ("Not met").

TC-VC-006 — View venue details and availability (read-only)

Test Scenario: Coordinator views one venue's details for the event date

Pre-conditions:

Venue A has photos, 30 min setup and 45 min turnaround; the event runs 10:00–12:00.  
Another event's booking at Venue C overlaps the event's occupied time.

Test Steps:

Select View details on Venue A; browse its photos.  
Choose Venue C in the panel.

Test Data:  
Venue A, Venue C

Expected Result:  
Venue A's photos and all details are shown with no editable field; it is Available, occupied 09:30–12:45 including setup and turnaround. Venue C is "Unavailable – booking" and its conflicting booking period is listed.

TC-VC-007 — Compare two venues

Test Scenario: Side-by-side comparison through the toggle

Pre-conditions:

Event Coordinator is viewing Venue A's details.

Test Steps:

Check that no second panel is shown.  
Select Compare side by side, then Compare on Venue B.  
Select Hide comparison.

Test Data:  
Venue A, Venue B

Expected Result:  
The second panel is hidden by default; after the toggle, Venue A and Venue B are shown side by side (stacked on mobile); hiding the comparison removes the second panel.

TC-VC-008 — Select a venue

Test Scenario: Coordinator selects the preferred venue

Pre-conditions:

The event is Under Review or in Planning.  
Venue A can hold the expected attendance.

Test Steps:

Select Select on Venue A and confirm.

Test Data:  
Venue A

Expected Result:  
Venue A is shown as Suggested; the event history has a "Coordinator suggested Venue A" entry; the Organiser receives a "Venue suggested" notification. No hold or booking is created.

Test Scenario: Selection is refused for an unsuitable venue

Pre-conditions:

Test Data:  
Venue B (too small), Venue C (inactive)

Expected Result:  
Venue B's Select button is disabled with the reason; selecting Venue C is refused ("This venue is no longer available for new requests") and nothing changes.

TC-VC-010 — Duplicate and stale selection

Test Scenario: Resubmission and a selection changed elsewhere

Pre-conditions:

Venue A was suggested.

Test Steps:

Test Data:

Expected Result:

Test Scenario: Organiser opens their request after the coordinator's selection

Pre-conditions:

Test Data:

Expected Result:

## SPM-74 — View Venue Availability

As an Event Coordinator or Venue Staff, I want to view a venue availability calendar across dates and times, including confirmed bookings, active holds, setup and turnaround buffers, and operational blocks, so that I can accurately determine when a venue can be requested without creating scheduling conflicts.

ACs:

* Only authenticated Event Coordinators and Venue Staff can access venue availability calendars.

    * Event Coordinators view availability inside the event request's Venue section: the calendar opens for the venues being viewed or compared, on the event's date, with the event's time already checked. There is no separate availability page for Event Coordinators.
    * Venue Staff view availability for venue management and booking decisions at Venues > Availability.
    * Event Coordinator Leads and other roles receive an access-denied response.

* Each venue in the event's Venue section shows its availability status for the event's date and time, including setup and turnaround time; the event's own bookings and holds never make it unavailable.
* The calendar displays venue availability for a selected date range and time period.
* Each calendar entry identifies:

    * Venue name
    * Date and time
    * Availability status
    * Entry type, such as confirmed booking, active hold, or operational block
    * Related event or booking reference where applicable

* Confirmed or approved bookings are displayed as unavailable periods.
* The calendar must prevent the same venue from appearing available when another active booking overlaps the requested occupied period.
* Active tentative holds are displayed as unavailable and must include their expiry date and time.
* Expired holds must no longer block the venue or appear as active availability restrictions.
* Operational blocks created by Venue Staff are displayed as unavailable periods.
* The calendar identifies the block reason, such as:

    * Maintenance
    * Equipment failure
    * Renovation
    * Safety
    * Other

* The block note is visible to authorised users.
* The system identifies overlapping occupied periods between bookings, holds, and operational blocks.

    * Adjacent periods are allowed.
    * Any overlap, including an overlap of one second, is treated as a conflict.

* The system clearly distinguishes between:

    * Available
    * Unavailable due to confirmed booking
    * Unavailable due to active hold
    * Unavailable due to operational block
    * Potentially suitable with an operating-hours warning
    * Availability not checked (the availability data could not be read)

* A venue cannot be shown as available if its occupied period conflicts with an active booking, hold, or operational block.
* If any part of the occupied period falls outside the venue's operating hours, the calendar displays a warning.

    Operating-hours violations are warnings rather than automatic booking blocks.

* The calendar reflects the latest committed booking, hold, block, and cancellation changes after refresh or reload.

    The system must not show a venue as available before a successful backend update is completed.

* The calendar provides appropriate feedback when:

    * Data is loading
    * No venues or availability entries exist
    * The requested date range has no records
    * The availability request fails
    * The user does not have permission to view the calendar

## Test Cases

Test cases 1–10 and 12–15 are unchanged, except that an Event Coordinator opens the calendar from the event request's Venue section (Show availability calendar) and Venue Staff from Venues > Availability. Test case 11 is revised and 16–18 are added.

### 11. Negative Testing – Unauthorised User (revised)

1. **Scenario:** Prevent an unauthorised user from viewing the calendar
2. **Pre-conditions:** User is logged in as an Event Coordinator Lead, Organiser, Technical Support or Attendee; separately, an Event Coordinator
3. **Test steps:**

    1. Navigate directly to `/venues?view=availability`
    2. Request availability data directly

4. **Expected Result:**

    * Event Coordinator Leads and other roles are denied and no availability information is exposed
    * An Event Coordinator opening `/venues` is told the page is not available for their role and finds availability in the event's Venue section

### 16. Happy Path – Calendar from the event request

1. **Scenario:** Coordinator opens the calendar for venues being considered
2. **Pre-conditions:** Coordinator is assigned to an event on 20 Nov 10:00–12:00; Venue A is open in the details panel and Venue B in the comparison panel
3. **Test steps:**

    1. Select Show availability calendar

4. **Expected Result:**

    * The calendar shows Venue A and Venue B on the event's week, with no venue picker
    * The requested period is pre-filled with the event's date and time, and the check result is shown

### 17. Happy Path – Availability on the event date in the venue list

1. **Scenario:** Venue cards show availability for the event
2. **Pre-conditions:** Venue A is free; Venue B has a booking ending 09:30 with 45 minutes turnaround; Venue A has 30 minutes setup; the event runs 10:00–12:00
3. **Test steps:**

    1. Open the event's Venue section

4. **Expected Result:**

    * Venue A shows Available, occupied 09:30–12:45 including setup and turnaround
    * Venue B shows Unavailable – booking, because the turnaround runs until 10:15

### 18. Boundary Testing – The event's own booking

1. **Scenario:** An event's own booking or hold does not conflict with itself
2. **Pre-conditions:** The event already has a booking at Venue A for its own time
3. **Test steps:**

    1. Open the event's Venue section

4. **Expected Result:**

    * Venue A is shown as Available for the event
