# SPM-174 Lead assignment integration

The Lead assigns submitted requests to active Coordinators. First assignment
enters `UNDER_REVIEW`; reassignment preserves the current lifecycle state.
Only the supervising Lead can reassign. An active legacy event without a
recorded supervising Lead is available to any Lead; its next reassignment
records that Lead. Coordinator self-assignment is not enabled.

## Database rollout

Development project: `rvwiflsedoujspmzfrbq`.
Applied migration: `20261020075714_spm174_lead_assignment_conflict_guard.sql`.
The local filename matches the version recorded by Supabase MCP. This is an
additive migration over the existing deployed assignment functions/history,
not a replay of older migrations or a replacement schema.

- `event_guard_coordinator_schedule` prevents new active overlaps on event
  inserts and changes to coordinator, scheduling times or active status. It
  locks the target coordinator profile until transaction commit, using the
  same serialization point as the assignment RPCs. Intervals are `[start,end)`.
- Existing legacy overlaps can retain their assignment/window and proceed
  through active states; changing the window/coordinator must pass the guard.
  Terminal/Draft events do not consume availability.
- `list_lead_event_assignments` validates an active trusted Lead and returns
  supervised or legacy unsupervised active assignments, including conflict
  flags. `reassign_event_coordinator` enforces that same supervision boundary
  after locking the event and checks the expected current coordinator.
- Both RPCs use a fixed `search_path` and grant execution only to the server's
  service role. The trigger helper has no client execution grants. Existing
  RLS and table grants are retained; browser business calls use Express.
- Event/history/activity/notification writes are in the same transactional
  RPC. Rejected, stale or conflicting operations have no partial effects.

The approved rollout preserved all 42 pre-existing synthetic events and their
assignments (105 overlap pairs). No cleanup, backfill or automatic reassignment
was performed. Leads resolve these explicitly in the Assignments page.
The full `event_no_overlapping_coordinator_assignment` exclusion constraint
is still deferred until no active overlap pairs remain. Its older migration
preflight deliberately refuses overlapping data; do not run a blanket push of
pending historical migrations against this shared database.

Deploy this migration before the backend that calls the new read RPC, then
deploy the frontend. Retain `ENABLE_COORDINATOR_WORKFLOWS=true`. Rolling the
applications back can retain the additive database objects. Any database
rollback needs a separately reviewed migration restoring the prior function
definitions; removing the guard would permit new overlaps. This migration
rewrites no existing business rows.

The hosted suite covers another Lead's denial, real Auth/Express/PostgREST/RPC

commits, with the loser retaining its unassigned state and no notifications.
It also holds a direct service-role insert open on one PostgreSQL connection,
observes a second connection waiting on the coordinator lock, commits the first
and verifies that the second receives `23P01/COORDINATOR_CONFLICT` from the guard.
