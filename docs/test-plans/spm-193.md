## Helper contracts for the deferred workflows

These helpers currently have no production callers on this branch. Call each
with `PERFORM` inside the workflow's own function, after its writes,
so the notice commits or rolls back with the action. Each goes to the event's
coordinator at the time of the call (none if unassigned or inactive) and sets
an action key, so a repeated call writes nothing.

| Caller | Function | Action key |
| --- | --- | --- |
| SPM-188 hold reminder (AC8) | `_notify_coordinator_hold_expiring(event_id, hold_id, venue_id, expires_at)` | `HOLD_EXPIRING:{hold}:{expiry}`, so an extended hold warns once more |
| SPM-188 hold expiry (AC8) | `_notify_coordinator_hold_expired(event_id, hold_id, venue_id)` | `HOLD_EXPIRED:{hold}` |
| Venue block on a booking (AC5, Master 5.4.4) | `_notify_coordinator_venue_blocked(event_id, block_id, venue_id, reason)`; reason is the block's reason code | `VENUE_BLOCKED:{block}:{event}:COORDINATOR` |
| Technical decision (AC6) | `_notify_coordinator_technical_decision(event_id, request_key, 'APPROVED' or 'REJECTED', reason)`; a rejection needs its reason | `TECHNICAL_REQUEST_{decision}:{request}:COORDINATOR` |

Hold, block and request IDs must match `[A-Za-z0-9_.-]{1,64}`.

## Triggers that already notify the coordinator

| AC | Function | Retry protection |
| --- | --- | --- |
| AC1 | `assign_event_coordinator` | Retry refused: the event is no longer `SUBMITTED` |
| AC2 | `reassign_event_coordinator` | Retry refused: `ASSIGNMENT_CHANGED` |
| AC3 | `post_clarification_message`, `save_clarification_amendments` via `_notify_clarification_party` (SPM-41 v2 has no resubmit) | Idempotency key; once until the coordinator reads the request |
| AC4 | `decide_venue_booking` (SPM-181/186/189) | Action key |
| AC5 | `set_venue_status` (venue taken out of service) | Action key |
| AC7 | `decide_safety_review` | Idempotency key |

First assignment prevents duplicate notices by refusing the repeated transition
out of `SUBMITTED`; it does not return a stored successful command response.
The TC-16 integration case sends the same `Idempotency-Key` header twice and
checks that the refused retry leaves one notice. The header is not used by
this branch's first-assignment handler. This is duplicate-effect prevention,
not proof of stored replay after a lost response or session reload.

## API

`/api/notifications` (list, unread count, mark one, mark all) is open to
`ATTENDEE`, `ORGANISER` and `COORDINATOR`; other roles get `403`. A hidden or
another user's notification is `404`. Coordinator targets are `EVENT_WORKSPACE`
(`/events/<id>`); after reassignment that page is `404` for the previous
coordinator (AC9).
