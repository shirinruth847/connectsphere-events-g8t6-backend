# SPM-155 attendee notifications

Story SPM-155 (epic SPM-31), subtasks SPM-156 to SPM-162, on
`feature/SPM-155-attendee-notifications`. Backend only; the Notifications
page (SPM-161) is a separate frontend change.

The shared foundation (SPM-156), the attendee notification functions and the
24-hour reminder job (SPM-158) are built for real. The workflows that trigger
AC1-AC3 (registration SPM-134, waitlist and offers SPM-163, cancellation) do
not exist yet, so nothing calls those functions in production. Tests call
them through stand-in workflow functions that exist only inside the isolated
test engine; there are no fake routes or endpoints.

## Functions future tickets call

Each is called with `PERFORM` inside the workflow's own database function,
after its writes, so the notification commits or rolls back with the action
(Master 7.1, 8). Each sets a unique `notification.action_key`, so a repeated
call writes nothing.

| Caller | Function | Recipients | Action key |
| --- | --- | --- | --- |
| SPM-134, SPM-163 (AC1) | `_notify_registration_recorded(registration_id)` | The attendee; wording follows REGISTERED or WAITLISTED | `REGISTRATION:{id}:{status}:{registered at}` |
| SPM-163 (AC3) | `_notify_place_offered(registration_id, offer_id, expires_at)` | The waitlisted attendee; sets `action_expires_at` | `WAITLIST_OFFER:{offer_id}` |
| Cancellation (AC2) | `_notify_event_cancelled_attendees(event_id)` | Active REGISTERED and WAITLISTED attendees | `EVENT_CANCELLED:{event}` |
| SPM-173 `confirm_event` (AC5) | `_notify_event_changed_attendees(event_id, previous_snapshot, current_snapshot)` | Active REGISTERED and WAITLISTED attendees | `EVENT_CHANGED:{event}:v{version}` |
| Any role's workflow | `_notify_event_users(event_id, title, message, recipients[], type, action_key, action_expires_at)` | Caller's choice | Caller's choice |

Cancellation must keep registrations REGISTERED or WAITLISTED (the CANCELLED
event closes them). Marking them WITHDRAWN would hide the cancellation notice
under AC6.

## Routes

All require `requireAuth` and work for every role; each user reaches only
their own notifications.

| Method and path | Response | Errors |
| --- | --- | --- |
| `GET /api/notifications?limit&cursor` | `{ notifications, nextCursor, unreadCount }` | 400 `VALIDATION_FAILED`, 401 |
| `GET /api/notifications/unread-count` | `{ unreadCount }` | 401 |
| `POST /api/notifications/read-all` | `{ updated, unreadCount }` | 401 |
| `POST /api/notifications/:id/read` | `{ notification, unreadCount }` | 404 `NOTIFICATION_NOT_FOUND`, 401 |

## Attendee event details (AC4, AC5)

"Go to Event" opens the event details dialog on My Events, which reads the
SPM-34 endpoint `GET /api/events/discovery/:id` (attendee-only). The endpoint
now also serves events the attendee holds a place on. No migration.

1. An attendee with a REGISTERED or WAITLISTED registration for the event (the
   `_notification_visible` rule) can open it in any status, including past and
   cancelled events.
2. Full details only when the event is published and CONFIRMED, PREPARATION or
   COMPLETED, whose current values are the confirmed ones.
3. Otherwise (PLANNING, SAFETY_REVIEW, CANCELLED, unpublished) only the title
   and status: `description`, `startDatetime`, `endDatetime`, `location`,
   `organisationName`, `registrationOpenAt` and `registrationCloseAt` are null
   and `detailsWithheld` is true. `TODO(SPM-173)` in `eventModel.js` marks the
   switch to the last confirmation snapshot (Master 5.7) once SPM-173 is merged.
4. Without such a registration the SPM-34 discovery rule is unchanged
   (published, CONFIRMED or PREPARATION, not yet ended); anything else is the
   same 404.

Added fields: `attendeeStatus` (`CONFIRMED` for CONFIRMED and PREPARATION,
`PENDING_CONFIRMATION`, `CANCELLED`, `COMPLETED`), `detailsWithheld` and
`myRegistration` (`{ status, registeredAt }` or null). Never returned: the
lifecycle state, purpose, internal notes, organiser identity, other attendees,
seat counts or any venue other than a single approved one. SPM-163 adds
`myRegistration.offer` for Accept Slot and Decline.

Unit tests cover each status, unpublished events, the registration lookup and
the discovery fallback. Live cases in
`tests/integration/attendeeEventDiscovery.integration.test.js`: a cancelled
event is withheld for its waitlisted attendee and 404 for another attendee; an
event back in planning is withheld; a past confirmed event is shown to its
registrant only.

## Dependency on SPM-173

None of SPM-155's migrations, functions or tests needs an SPM-173 object. All
four migrations apply on the PGlite test schema with no SPM-173 objects, and
SPM-173's four-argument `_notify_event_users` (`CREATE OR REPLACE`) applies
afterwards beside SPM-155's seven-argument overload, which has no defaults, so
each call resolves to one function. SPM-173 does not call SPM-155 functions;
wiring `confirm_event` to `_notify_event_changed_attendees` (AC5) is a
follow-up once both are merged. Either merge order works. SPM-173's
migrations carry earlier timestamps (`20261019…`), so deploying SPM-155 first
with `supabase db push` would need `--include-all` for SPM-173 later.

## Deployment

Applied to shared development on 20 October 2026, in order, using the
Supabase migration capability:

- `20261020161808_spm155_notification_types.sql`
- `20261020161837_spm156_notification_foundation.sql`
- `20261020161912_spm155_attendee_notifications.sql`
- `20261020161924_spm158_event_reminders.sql`

All are additive: six enum values, two nullable columns, two indexes and new
functions created with `CREATE FUNCTION`. No existing row or function was
changed; SPM-173's four-argument `_notify_event_users` stays as it is beside
the new seven-argument overload. Rollback needs a reviewed migration that
drops the new functions, indexes and columns; enum values cannot be removed.

The reminder job starts with the server (`EVENT_REMINDER_INTERVAL_MS`, default
5 minutes, 0 turns it off). It has no HTTP trigger.

## Verification

```sh
npm test
PGLITE_MODULE=/path/to/@electric-sql/pglite node --test tests/database/*.test.cjs
npx jest tests/integration/notifications.integration.test.js --runInBand   # needs TEST_DATABASE_URL
npm run seed:notifications && npm run seed:notifications:cleanup           # dev only
```

The live suite uses `spm32-<run>` accounts and events and removes them with
their registrations and notifications. Reminder cases run in rolled-back
transactions so they never send reminders for anyone else's data.

The dev seed gives `dev-attendee@connectsphere.test` seven visible
notifications on five unpublished "[DEV SEED SPM-155]" events, plus one that
must stay hidden (AC6); the reminder job adds an eighth for the event starting
in 23 hours. Cleanup removes exactly the manifest's events with their
registrations and notifications.
