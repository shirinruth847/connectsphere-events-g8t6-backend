# SPM-192 organiser notifications

Story SPM-192 (epic SPM-31), subtasks SPM-253 to SPM-259, on
`feature/SPM-192-organiser-notifications`. The organiser Notifications page
(SPM-258) is the frontend part of the same story.

Migration `20261026043658_spm192_organiser_notifications` (applied to the
development project):

- `_notification_visible`: an organiser sees a notification only while they
  own its event, and none without an event (AC8). Attendees unchanged; staff
  still see what is addressed to them until SPM-193.
- Owner-notice helpers for the dependent workflows. Call each with `PERFORM`
  after the transition, inside the workflow's own function. Each checks the
  event is in the state it announces (`EVENT_STATUS_MISMATCH` otherwise) and
  sets an action key, so a repeated call writes nothing.

| Caller | Function | Action key |
| --- | --- | --- |
| SPM-39 accept feasibility (AC3) | `_notify_feasibility_accepted(event_id)` | `FEASIBILITY_ACCEPTED:{event}` |
| Rejection (AC3; current Jira SPM-40, despite SPM-192's older dependency label) | `_notify_event_rejected_owner(event_id, reason)`; blank reason refused | `EVENT_REJECTED:{event}` |
| Cancellation workflow (AC5), alongside `_notify_event_cancelled_attendees` | `_notify_event_cancelled_owner(event_id)` | `EVENT_CANCELLED_OWNER:{event}` |

`/api/notifications` (list, unread count, mark one, mark all) is open to
`ATTENDEE` and `ORGANISER`; other roles get `403` until SPM-193. Organiser
targets are `EVENT_WORKSPACE` (`/events/<id>`).

Submission (AC1), assignment (AC4), clarification (AC2), confirmation (AC5)
and coordinator edits (AC6) already notify the owner from their own functions;
their existing transaction boundaries are preserved. Reassignment uses the
command replay protection below; comparing coordinator IDs alone does not
prevent replay after an intervening A -> B -> A sequence.

## AC10 reassignment replay correction

Migration `20261028010000_spm192_reassignment_replay.sql` is prepared locally;
it has not been applied to shared development. The reassignment form sends an
`Idempotency-Key` with `PATCH /api/events/:id/coordinator`; first assignment
is unchanged. Missing or invalid reassignment keys return `400`; reusing a key
with another event or payload returns `409 IDEMPOTENCY_KEY_REUSED`.

`reassign_event_coordinator_idempotent` rechecks the active Lead and supervision
under the event lock before looking up the command. It invokes the installed
four-argument reassignment function and stores its result in the same database
transaction as the assignment, history and notifications. Replays return the
original result (`replayed: true`, `Idempotent-Replayed: true`) without repeating
any write, even after another command changed the coordinator again. The client
then refreshes current assignments rather than showing the historical result
as the current assignment. Lost responses, 5xx and expired sessions retain the
original key/payload in user-scoped session storage across refresh and reload.

The wrapper preserves later SPM-193 changes to the underlying function. Its
constraint extension also retains every previously allowed idempotency operation
and existing response. It creates no fixture or business rows during deployment.
The constraint replacement takes an exclusive table lock and validates existing
rows; schedule it with other migrations rather than holding application
transactions open.

Deploy the migration first, then the matching backend/frontend together; older
frontends lack the required key and older backends ignore it. Rollback must stop
reassignment writes before reverting to the old backend, which lacks replay
protection. Retain command records and the additive function/constraint; do not
edit already-applied migration files or restore old notification visibility.

## Dependency boundary and current evidence

SPM-192 supplies notification helpers, inbox access and reliability. This fix
does not implement SPM-39's feasibility decision, SPM-40's rejection decision,
or the separate cancellation workflow. AC3 and AC5 cancellation remain pending
real workflow integration on this branch; passing stand-ins is not full AC
completion. Each caller must validate its own actor, lifecycle, reason and
resources and call the notification helper inside its transaction.

Read-only development inspection on 28 October found both original SPM-192
migrations applied, plus newer SPM-39/SPM-193 migrations outside this PR. The
installed SPM-39 function writes its own notice; do not additionally invoke
the feasibility helper there and send a second notice. Coordinate a single
notification producer when that dependency is integrated. No shared writes or
hosted fixture tests were authorized or performed for this correction.
