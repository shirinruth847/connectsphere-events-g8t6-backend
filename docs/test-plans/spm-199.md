## Contract and scope

The new GET `/api/events/:id/arrangements` is an organiser-safe view after
the existing role and event-relationship checks. Existing event overview,
coordinator name, backend status labels and audience-filtered history are
retained. Same-organisation submitted-event visibility is preserved; a
colleague's private draft remains inaccessible. No staff workflow, resource
mutation, lifecycle transition or new database table is introduced.

Each of `venues`, `technical` and `safety` reports READY or UNAVAILABLE.
Venues additionally report holds and availability independently so MongoDB
failures do not hide readable PostgreSQL bookings. Only READY sections have
data arrays; the frontend treats UNAVAILABLE as an error, never an empty list.
Provider errors are logged server-side using bounded metadata, not returned.

## Dependencies and deployment

Read-only Supabase MCP inspection of development project
`rvwiflsedoujspmzfrbq` succeeded during the independent review on 25 October
2026. A subsequent catalog recheck during the fix confirmed the existing
venue operational fields and the absence of primary flags and resource tables.
The baseline uses `venue_booking.room_id` and `equipment_request`. The primary flag, direct
venue booking link, combined technical requests and resource incidents are
an existing unapproved draft at `supabase/drafts/20261019100400_master_resource_tables.sql`.
That draft is not promoted or applied by this ticket. The reader has compatibility
paths for those proposed structures, tested with mocks; this does not establish
that the draft has been deployed or that its hosted grants/RLS are correct.

Until those owners deploy the resource baseline, multiple legacy bookings
cannot supply an explicit primary, combined technical support details cannot
be verified, and persisted incident resolution data cannot be loaded. The UI
reports these limits. Safe block detection still uses the MongoDB calendar
and setup/turnaround minutes; missing minutes yield unknown availability.
Known PostgreSQL venue unavailability is still shown per active arrangement:
`status` INACTIVE/UNDER_MAINTENANCE or `is_active = false` produces the safe
pending-coordinator message even when calendar/buffer/incident reads are missing.
No private venue reason is selected or returned, and booking decisions remain intact.
Staff-only legacy technical/support notes are intentionally excluded because
there is no organiser-safe visibility marker.

The final version check is optimistic: PostgreSQL resource writers must call
SPM-250's supersession helper inside their transaction. It does not promise a
single snapshot across MongoDB and PostgreSQL. A failed version-check query
fails the complete response; no stale approvals are returned. All venue
projections use the clock after every section and the version check complete.
Inactive bookings/holds and completed occupied periods do not gain current
unavailability warnings; turnaround is included when known. Resolved incidents
remain visible historically, while a currently unavailable venue takes priority
over an earlier restoration for an active arrangement.

No shared migrations, MongoDB schema changes, seed data or real-user changes
were applied. Local tests use mocks and a temporary local MongoDB, with its
binary cached under `/private/tmp/spm199-mongodb-binaries`.
